### 1.0 ユーザーに確認する点

**N03 は決定済み（2026-11-17）**: ユーザーが (A) を選んだ（「技術検証なので問題ない」）。下の 1 は判断の経緯として残す。

1. **N03（行政区域）の扱い**。ページは CC BY 4.0 だが、同梱メタデータが「本製品を複製する場合には、国土地理院の長の承認を得なければならない。」と述べる。選択肢は次の 2 つ。
   - (A) N03 を使い続ける。公開・商用の前に、国土交通省（国土数値情報の問い合わせ窓口）へ測量法上の扱いを問い合わせる。回答までは検証用に限る。
   - (B) 候補に差し替える（2.3.1。e-Stat 境界データか、国土地理院の地球地図日本）。いずれも条件の確認が済んでいない部分がある。
2. P29（学校）は、ページの原典欄に「測量法に基づく国土地理院長承認（使用）R 3JHs 917」がある。同梱メタデータには、複製の承認に関する文はなく、N03 と同じ定型の使用制限文があるだけ（2.5）。N03 より弱い記載と見ており、判定は利用可のままにした。ただし 1 と同じ問い合わせの中で併せて確認してよい。

**注意点（変換時に必要な判断）**

- 形状は線で、駅が点ではない。設計どおり重心の点に変換する。

## 3. 取得手順

```
./scripts/data/download.sh
```

- 取得先の一覧はスクリプト先頭の `DATASETS` 配列。取得済みの zip と展開済みのディレクトリはスキップする。
- リクエストは直列で、間に 5 秒の間隔を置く。リトライは 1 回だけ。
- 各 zip は `data/raw/<ID>/` に置き、同じ場所に展開する。展開済みの印は `.unpacked-<zip名>`。
- 2026-11-17 の初回実行は約 5 分（N03 の 766 MiB が大半）。
- 各 zip は、取得直後と、取得済みでスキップするときの両方で、バイト数と sha256 を検証する（`DATASETS` に値を持つ）。取得直後に不一致なら `.part` を破棄して失敗し、既存の zip が不一致なら自動では削除せず、内容の確認と手動削除を促して失敗する（HTML のエラーページが zip として保存される事故への備え）。
- 展開前に、`unzip -Z1` で絶対パスと `..` を含むエントリを、`unzip -Z` のモード列でシンボリックリンクを調べ、あれば展開を拒否する（macOS 標準の Info-ZIP で動く方式。一時ディレクトリに展開して移す方式は採らなかった）。

## 5. 変換: 行政区域（タスク 1.3）

`municipalities` と `prefectures` を、N03 の raw データから 1 つのコマンドで作る。N03 以外の 4 種はタスク 1.4 で同じコマンドに足した（6）。カタログ（1.5）、アップロード（1.6）は、この上に足す。

### 5.1 コマンドと出力

```
npm run data:convert      # リポジトリ直下で実行。先に ./scripts/data/download.sh で raw データを取得しておく
```

- 行政区域の 2 つの出力が読むのは `data/raw/N03/N03-20260101.shp`（258 MB の Shapefile。GeoJSON は 580 MB）だけ（コマンド全体は、6 の 4 種の raw ファイルも読む）。書くのは `data/work/` と `data/dist/` だけ（なければ作り、前回の出力は消してから作り直す）。raw ファイルがなければ、取得コマンドを示して失敗する。行数が期待（市区町村 1,898、都道府県 47）と違うとき、mapshaper が失敗したときも、メッセージを出して終了コード 1 で終わる。
- 出力: `data/dist/municipalities.parquet`（`muni_code`、`pref_name`、`city_name`、`muni_name`、`geom`）、`data/dist/prefectures.parquet`（`pref_code`、`pref_name`、`geom`）。GeoParquet（DuckDB spatial が書く。`geo` メタデータ: version 1.0.0、主列 `geom`、WKB、`MultiPolygon`、bbox）、zstd、行グループ 2,048 行（どちらも 1 行グループ）、座標は元のまま（経度・緯度、JGD2011。再投影なし）、コード順。NULL なし。
- 設定は `scripts/data/datasets.config.ts` の 1 か所（ファイルの場所、属性名の対応、島の面積、簡素化の強さ、mapshaper のヒープ、出力先）。行グループと圧縮は `shared/config.ts` の `dataConfig.geoParquet` を使う。純粋関数（引数、SQL、検査）は `convert-plan.ts`、処理の流れは `convert.ts`。単体テストは `*.test.ts`（変換そのものは単体テストでは走らせない）。6 の 4 種のモジュールは 6.1。

### 5.2 方法

| 順 | 道具 | 処理 |
|---|---|---|
| 1 | DuckDB（`@duckdb/node-api`、spatial） | 所属未定地の 2 条件（コード末尾「000」、`N03_004 = '所属未定地'`）が同じ行を選ぶことを確かめる（NULL を含めて比べる。141 行 = 7 コードで一致）。未定地を除いた raw のポリゴンに出力の属性列を付け、`data/work/municipalities_raw.parquet` に書く（中間ファイル。5.7） |
| 2 | mapshaper（`mapshaper-xl`、引数配列で子プロセスとして起動） | 入力を `snap` つきで読む（下）→ 未定地を除く（`-filter`）→ `N03_007` 以外の属性を捨てる → `-simplify weighted interval=250m keep-shapes` → `-dissolve N03_007` → GeoJSON（`data/work/municipalities_simplified.geojson`）。簡素化は 124,989 ポリゴンを一緒に行うので、隣り合う市区町村が共有する辺は 1 回だけ簡素化される |
| 3 | DuckDB | 市区町村ごとのパートを `ST_Dump` で分け、楕円体上の面積（`ST_Area_Spheroid`）を求める。面積が 100,000 m²（0.1 km²）未満で、他のコードのパートと頂点を共有せず（接しない）、その市区町村の最大のパートでもないものだけを捨てる（本当の島）。他の市区町村に接する小さなパート（飛び地・池など）は残す。市区町村の境界で分かれた小さな島（72 パート、合計 0.26 km²。レビューでの数え方）も、規則どおり、接するので残る。最大のパートは面積にかかわらず残し、面積が同じなら id の小さいほうを最大とする。`ST_Collect` → `ST_Multi` |
| 4 | DuckDB | `ST_IsValid` が偽の行を数え、偽のものだけ `ST_MakeValid`（面のパートだけ残す）で直し、もう一度数える。行数を検査して `municipalities.parquet` を書き、書いたファイルを読み戻して行数をもう一度検査する |
| 5 | DuckDB | 4 の結果を都道府県コード（`muni_code` の先頭 2 桁）で `ST_Union_Agg` し、4 と同じく数えて直し、検査して `prefectures.parquet` を書く |

- **入力の `snap`**: raw の Shapefile では、隣り合う市区町村の境界の頂点が bit 単位では一致していない（差は最大で約 2.2e-13°。レビューでの測定で、3 市区町村で測ったもの。全国で測ったものではない）。mapshaper は座標が完全に一致するときだけ辺を共有として扱うので、`snap` なしでは境界が片側ずつ別々に簡素化され、簡素化後の隙間（177 個）と、直せない交差（557 か所）ができた。`snap`（既定の距離は約 1.1e-13°。mapshaper のソース `mapshaper.js` で確認）を付けると、81,324 点が動き（`[i] Snapped 81324 points`）、隙間は 0 個、直せない交差の報告もなくなった。動く距離は無視できる大きさで、「座標は元のまま」とは実質的に矛盾しない。設定は `datasets.config.ts` の `mapshaper.snap`。`snap` で出力の面積が +21.88 km² 変わる（`snap` なしの版との比較）。レビューでの測定では、内訳は `snap` による +17.65 km²（うち 17.2 km² は簡素化していない土地の内側にあり、結果は元のデータに近づいた。元との差 −210 → −192 km²）と、残した飛び地 +4.23 km²。`snap` なしの版が海岸側でより多く土地を失った理由は、確かめていない。
- 「接する」の判定は、パートの頂点を座標の等値結合（`part_vertices`、`part_contacts`）で調べる。`snap` のあとは、共有する境界が同じ頂点でできているので足りる（`snap` を切ると、この判定が境界を見落とし、飛び地がまた捨てられる）。`ST_Intersects` の結合は約 120 秒かかったので使わない。この判定を含め、全体で約 11 秒。
- 名前: `muni_name` は `N03_004` に `N03_005`（政令市の区名。なければ空）を連結した文字列（札幌市中央区。特別区は `N03_004` の区名のまま）。`city_name` は `N03_004`。この式は SQL の 1 か所にだけある。
- 各市区町村の最大のパートを残す処理は、mapshaper の `-filter-islands` では実現できなかったので、自前の手順（手順 3）にした。`-filter-islands min-area=1000000000 remove-empty` では 1,849 行に減った（最大のパートも落ちる）ので、使っていない。規則は、小さな表を使った単体テスト（spatial 拡張なしの DuckDB。最大のパートが残る、他に接する小さなパートが残る、島が落ちる、面積が同じでも順序が決まる、など）で確かめている。
- 規則が行数を支えるかの確認（`snap` なしの版で、`min-area` を上げた試行。出力は書かず、プロセス内で数えた。接する条件を入れる前の数字で、面積だけの条件）: 3.5 km² で最大のパートだけで残る市区町村が 2（舟橋村、渡名喜村）、5 km² で 14、10 km² で 79。どれも行数は 1,898 のまま。採用した 0.1 km² では 0 件（最小の「最大のパート」は渡名喜村の約 3.04 km²）なので、採用した値では、この規則は保険として働くだけ。
- mapshaper のヒープ: 1 GB の `mapshaper-xl 1gb` でも通った（`snap` なしの版。最大 RSS 約 1.09 GB）。設定は 2 GB。この機械の Node の既定のヒープ上限は約 4.5 GB。
- **簡素化の記録**（測定したものすべて。島の面積は 0.1 km² 固定、行数はどれも 1,898、無効ジオメトリは 0。基準は、スパイクの 15 万頂点前後・2 MB 未満）:

  | 設定 | 頂点数 | `municipalities.parquet` のバイト数 | 判断 |
  |---|---|---|---|
  | `interval=200m`、`snap` なし、面積だけで島を除く | 181,293 | 1,720,309 | 頂点が基準を超える |
  | `interval=250m`、`snap` なし、同上 | 146,225 | 1,386,001 | 基準内（修正前の採用値） |
  | `interval=300m`、`snap` なし、同上 | 123,528 | 1,171,371 | 基準内だが、250 m で足りる |
  | **`interval=250m`、`snap` あり、接しない小さなパートだけ除く（採用）** | **146,233** | **1,382,701** | 基準内。上の 250 m とほぼ同じ |

  4 行目は修正（レビュー指摘への対応）のあとの値で、200 m と 300 m は `snap` つきでは測り直していない。スパイクの「200 m」は市区町村ごとの個別の簡素化（0.001° → 統合 → 0.002°）で、mapshaper の `interval=200m` とは同じ強さではない。そのほか、mapshaper 自身の `-filter-islands` と `precision=0.00001` で書いた GeoJSON を使う試行を 200/250/300 m で行っている（250 m で 889,941 バイト）。この版は採用していない。
- 座標の丸め（`precision=`）は設定していない（元の座標を保つ）。丸めると小さくなるが、辺が交わらないかは確かめていない。

### 5.4 共有境界（重なりと隙間）

測定は、書き出した 2 つのファイルに対して、GEOS（DuckDB spatial）で行った。面積は楕円体上の m²。

- **重なり**: 市区町村の組のうち、外接矩形が重なる 6,132 組を候補にし、`ST_Intersects` が真の 4,861 組で交差部分の面積を調べた。面積が 0 より大きい組は **0 組**（合計 0 m²）。都道府県も、接する 88 組、重なり 0 組。市区町村の面積の合計と和集合の面積は一致する（377,716,388,952 m²）。
- **隙間**: 全市区町村の和集合の穴（囲まれた隙間）は **0 個**、都道府県の和集合の穴も 0 個。`snap` なしの版（修正前）では 350 個（合計 6.97 km²）で、内訳は、除去した小さなパートの跡 173 個（3.38 km²）と、簡素化の隙間 177 個（3.59 km²。最大 0.39 km²。原因は境界頂点が bit 単位で一致しないこと）だった。前者は「他に接するパートは捨てない」規則で、後者は `snap` で消えた。mapshaper の出力（島の除去の前、全パート）の和集合の穴も 0 個。除去した所属未定地と重なる穴はもともと 0 個だった。
- **この数字が示すこと・示さないこと**: 示すのは、どの 2 つの市区町村も面積のある重なりを持たないことと、内側に閉じた隙間がないこと。示さないのは、海や湖に開いた隙間（穴として数えられない）、個々の境界線のずれの大きさ。タスク 1.4 の点の空間結合は簡素化していない中間ファイル（5.7）を使うので、この隙間の影響は受けない。ただし、簡素化した層（`municipalities.parquet`）に対する点の判定は、境界の近くや、除去した島の上では、外れうる（簡素化でずれるため）。

### 6.5 railways

- 方法: 21,933 区間を、路線名・運営会社・鉄道区分・事業者種別の 4 つの属性の組で 607 グループにまとめた（1 グループが 2 つのコードを混ぜることはない）。区間は WKT の文字列順に並べてから `ST_Collect` で束ね、つながるところを `ST_LineMerge` でつないだ（読み込む順に結果が依存しない）。つないだ結果は、465 本が LINESTRING、142 本が MULTILINESTRING で、頂点は 384,538（元は 404,646）。`ST_LineMerge` は 3 本以上が出会う点（分岐・合流）では線をつながないので、MULTILINESTRING は「分岐・合流がある」または「途切れた部分がある」路線である。142 本のうち、パートがすべてつながっているのは 124 本（分岐・合流だけ）で、途切れた部分を持つのは 18 本（測り方: 142 本をパートに分け、`ST_Intersects` で交わるパートを辺に見立てて、Union-Find で連結成分を数えた。成分が 1 つなら全部つながっている）。
- 簡素化: 目安の 15 万頂点を超えるので、`ST_SimplifyPreserveTopology`（Douglas-Peucker。各線の形が自己交差したり潰れたりしないようにする。線どうしの接続は保たない。下の分岐点の扱い）で簡素化した。許容差はメートルを度に直して（1 度 = 111,320 m）度の座標のまま適用する。東西方向では実際のメートルより少し大きくなる。3 つの設定を測った（バイト数は、鉄道区分と事業者種別をコードのまま書いた測定用のファイルのもの）:

  | 許容差 | 頂点数 | バイト数 | 判断 |
  |---|---|---|---|
  | なし（つないだだけ） | 384,538 | 3,082,518 | 目安を超える |
  | **10 m（採用）** | **71,639** | **614,890** | 15 万頂点以内で、最も軽い簡素化 |
  | 20 m | 50,859 | 444,167 | 採らない |
  | 30 m | 42,062 | 372,165 | 採らない |

  採用した設定の出力ファイルは 615,233 バイト（ラベルの分が増える）。頂点は LINESTRING が 31,794、MULTILINESTRING が 39,845。無効ジオメトリは 0 件。
- **分岐点の扱い**（10 m で簡素化した結果を、簡素化前と比べた）: 線の端（全部で 3,650 か所）は、すべて頂点として残る（頂点を落とすだけで、座標を動かさない）。ただし、他の路線の頂点の上に端があった場所（996 か所）のうち、相手の路線がその頂点を残したのは 278 か所だけだった。接していた路線の組（外接矩形ではなく図形が交わる組）は 1,385 組あり、簡素化後も接するのは 1,248 組で、137 組は接しなくなった（簡素化後に新たに接した組が 1 組あり、簡素化後に接する組は全部で 1,249 組）。接しなくなった 137 組の隙間は、最大 6.47 m、中央値 1.44 m（1 m を超えるのが 83 組、5 m を超えるのが 8 組。許容差 10 m より小さい）。路線の総延長は 27,815.5 km から 27,791.8 km（−0.085%）で、延長の集計には使える。向かないのは、線どうしの接続（交差、乗り換え）を使う解析。
- ラベル: `railway_type`（11 種。N02 に出ない 17 無軌条鉄道も表にある）、`operator_type`（5 種）。路線のグループ数と、区間の件数は 2.4 の件数と一致する（区間の件数は、事業者種別が 245、10,517、1,169、7,170、2,832。鉄道区分が 10,762、9,041、86、16、31、164、1,464、38、138、176、17）。ファイルは 1 路線 1 行なので、ラベルごとの行数は区間の件数ではなく路線の数（事業者種別: 新幹線 9、JR在来線 170、公営 44、民営 283、第三セクター 101）。
- 並び順: 運営会社、路線名、鉄道区分コード、事業者種別コード（文字コード順）。

### 6.6 schools

- 方法: P29 の 56,807 行をそのまま 1 行ずつ点にした（複数キャンパスの学校は複数行）。学校コード・休校区分・キャンパスコード・学校名備考の列は保持しない。学校分類（`P29_003`）と管理者コード（`P29_006`）を、`school_type`（13 種）と `admin_type`（5 種）のラベルにした。
- ラベルの件数は 2.5 の件数と、18 個（13 + 5）すべて同じ（例: 小学校 18,980、幼稚園 8,837、市区町村 32,019、民間 19,574）。
- 市区町村: 元の属性のコード（56,396 件）。`municipalities` にない 411 件（浜松市の旧区）は座標から引き直した（6.2）。

### 6.7 利用する人が知っておく注意（表ごと）

**land_prices**

- 1 行は地価公示の標準地 1 か所で、価格（`price_yen_per_m2`）は 1 ㎡あたりの円。2026 年（令和 8 年）1 月 1 日時点の価格だけが入る。
- `yoy_change_pct` は、新設の標準地と休止の標準地（合計 612 件）では NULL。元のデータでは、この 2 種に 0.0 が入っているが、変動がなかったという意味ではない。NULL でない 0.0（3,065 件）は本当の 0.0。
- 価格の偏りは大きい（470〜67,100,000、中央値 83,000）。平均ではなく、分位数で階級に分ける。
- `land_use` は用途区分（住宅地、商業地、工業地、宅地見込地、林地）で、利用の現況ではない。
- `address` は元のまま（都道府県名のあとに全角空白があり、数字は全角）。
- `muni_code` は標準地の属性のコードで、座標のある市区町村とは 16 件で違う（隣の区の境界付近）。地図で市区町村ごとに点を数え直すと、この 16 件は違う市区町村に入る。

**stations**

- 1 行は駅 × 路線の線 1 本で、点は元の線の重心。駅の位置の点ではなく、曲がった線では重心が線から外れることがある。同じ駅・路線でも複数行になる（行 10,263 に対し、駅名・運営会社・路線名の組は 10,153 種）。駅の数は行数では数えられない。同名の別の駅もある（駅名 8,503 種、駅名と市区町村の組 9,027 種）。
- `passengers_per_day` は 2024 年度の 1 日あたりの乗降客数。**NULL は、データなし、非公開、他の路線の行にまとめて記載、のどれか**（2,493 行）。元のデータはこれらに 0 を入れているが、乗降客数が 0 という意味ではない。値が 0 の 31 行だけが本当の 0。
- 乗り換え駅では、1 つの路線の行に、他の路線の分を含む値が入る。例: 渋谷駅の東急電鉄東横線の行（1,770,430）には、田園都市線と東京地下鉄の線の分が含まれる。路線別の値としては読めない。値は、駅ごとの合計として使うなら、NULL でない行をそのまま足せばよい（他路線の行は NULL なので、二重には数えない）。
- 乗降客数は各事業者が独自に算出した値で、基準が統一されていない。東日本旅客鉄道と北海道旅客鉄道の無人駅は「データなし」、九州旅客鉄道は上位 300 駅以外が「非公開」で、NULL になる。
- 2024 年度に駅がない 271 行（廃線など）は含めない。

**railways**

- 1 行は 1 つの路線（路線名・運営会社・鉄道区分・事業者種別が同じ区間をまとめたもの）。1 本の線につながったものは LINESTRING（465 行）。分岐・合流がある路線、または途切れた部分がある路線は MULTILINESTRING（142 行）。142 行のうち 124 行はパートがすべてつながっていて（分岐・合流があるだけ）、途切れた部分を持つのは 18 行だけである。**ジオメトリの型で「途切れた路線」を探してはいけない**（MULTILINESTRING の約 9 割は、つながっている）。
- `line_name` は N02 の路線名で、「東北線」のように JR の部分名になっていることがある。「東北本線」のような運行系統の名前と合わないことがある。同じ路線名が複数の行に現れる（路線名 553 種に対し 607 行。「本線」は 11 行で、10 の運営会社に分かれる。富山地方鉄道だけが 2 行）。路線名だけで絞ると、別の事業者の路線が入る。
- 同じ運営会社・同じ路線名でも、鉄道区分が区間で違えば 2 行になる（10 組。例: 富山地方鉄道の本線と富山港線、福井鉄道の福武線は、普通鉄道と軌道に分かれる。神戸新交通のポートアイランド線は、案内軌条式と案内軌条式鉄道に分かれる）。路線の数や路線ごとの延長を求めるときは、`operator`、`line_name` で集約する。
- 10 m の許容差で簡素化してある。線の形は粗く、接していた路線の組の約 1 割（1,385 組のうち 137 組）は接しなくなっている（隙間は最大 6.47 m、中央値 1.44 m）。路線の総延長は簡素化前から −0.085% で、延長の集計には使える。「X 線と接続する路線」を `ST_Intersects` や `ST_Touches` で求めるなど、線どうしの接続を使う解析には向かない（約 1 割を落とす）。
- 駅の位置は `stations` の座標とは別のデータ（駅の点が線の上にあるとは限らない）。
- `railway_type` と `operator_type` は日本語のラベル（例: 普通鉄道JR、民営鉄道）。

**schools**

- 1 行は学校 1 キャンパスの 1 点で、キャンパスが複数ある学校は複数行になる（学校コードは 56,318 種に対し 56,807 行）。学校の数としては、行数をそのまま使えない。学校名と所在地が同じ行が 2 組ある。
- 休校区分の列は保持していない（元のデータでは、半数近くが「調査なし」）。
- `school_type`（小学校、中学校、高等学校、大学など 13 種）と `admin_type`（国、都道府県、市区町村、民間、その他）は日本語のラベル。`admin_type` の民間は私立などを指す。
- `address` は都道府県名から始まり、空白なしで市区町村名（郡名を含むことがある）が続き、数字は半角（実測: 56,807 件中 56,801 件が `pref_name` で始まり、市区町村名（`city_name`）で始まるものは 0 件。残る 6 件は別の都道府県で始まる。例: 東京都町田市…で `pref_name` は神奈川県）。地価の住所は、都道府県名のあとに全角空白が入り、数字が全角で、この点が違う。
- 浜松市の旧区のコード（22131〜22137）の 411 件は、座標から新区のコード（22138、22139、22140）に引き直してある。中央区立の学校 3 件（中央区立泰明小学校、中央区立泰明幼稚園、中央区立城東小学校）は、元の属性のコードが千代田区（13101）で、座標は中央区（13102）のポリゴンの中にある。`muni_code` は元の属性のコードのままで、名前も千代田区になる（学校名と座標からは中央区と見え、元のコードの誤りの可能性が高い。地価の同じ比較では、16 件とも元のコードのほうが正しかった）。

## 7. カタログ（タスク 1.5）

LLM のシステムプロンプトに埋め込む、6 つのデータセットの説明（`shared/catalog.json`）。モデルが探索クエリなしに正しい SQL とスタイルを書けるよう、1 行が何か、値がどんな形か、どこに落とし穴があるかを、カタログ自身に書く。S3 には置かず、リポジトリのファイルにする。

### 7.1 コマンドと出力

```
npm run data:catalog      # data/dist/ の既存の 6 ファイルから、shared/catalog.json を作り直す（文章を直したとき）
npm run data:convert      # 変換の最後に、同じ処理でカタログを書く（出力とカタログがずれない）
```

- `data:catalog` は `data/dist/` の 6 ファイルだけを読み、`shared/catalog.json` だけを書く。ファイルが 1 つでもなければ、`npm run data:convert` を示して失敗する。DuckDB の spatial 拡張が要る（初回は DuckDB 自身が取得する）。
- 書く前に `shared/catalog-schema.ts` のスキーマで検証し、通ったときだけ書く。ファイルは追跡対象で、決まった形（2 スペース、末尾に改行、キーはスキーマの順、データセットは `municipalities`、`prefectures`、`land_prices`、`stations`、`railways`、`schools` の順、列はファイルの列順）。同じ入力から同じバイト列ができる。
- 生成側（変換とカタログの生成）は `shared/catalog.json` を読まない。ファイルがなくても、古くても動く。生成側のデータセット ID とその順序は `scripts/data/datasets.config.ts` の `datasetIds`、ファイル名の規則は `shared/dataset-files.ts`。実行時（バックエンド、ブラウザ、アップロードの検査）はカタログを読む（`shared/catalog.ts`、`shared/datasets.ts`）。この 2 つがずれると、`scripts/data/catalog.config.test.ts` が失敗する。
- 設定（1 か所）: 上位値の個数 10、全値を載せる列の上限 20、範囲の小数桁 5、大きさの上限 24,000 文字は `shared/config.ts` の `dataConfig.catalog`。ジオメトリ列の名前は `dataConfig.geoParquet.geometryColumn`（`geom`）。文章は `scripts/data/catalog.config.ts`。

### 7.2 測るもの

| 項目 | 方法 |
|---|---|
| 列の名前と型 | Parquet ファイル自身の `DESCRIBE`（変換の設定は見ない）。`VARCHAR` は `string`、整数と浮動小数は `number`、`BOOLEAN` は `boolean`。ジオメトリ列は除く。それ以外の型は、データ名・列名・型を示して失敗する |
| `geometryType` | `ST_GeometryType` の値から。POINT は `point`、LINESTRING と MULTILINESTRING は `line`、POLYGON と MULTIPOLYGON は `polygon`。2 つの種類が混ざると失敗する |
| `featureCount`、`bbox` | 行数と、ジオメトリ列の範囲（`ST_XMin` など）。範囲は 5 桁に外向きに丸める（最小は切り捨て、最大は切り上げ） |
| `stats` | 数値の列ごとに、NULL を除いた最小と最大 |
| `topValues`、`distinctCount` | 文章の設定で指定した文字列の列だけ。NULL を除き、件数の多い順、同数なら値の昇順。指定は 2 種類。**全値**（カテゴリの列）は、異なる値すべてを載せ、値の数が 20 を超えるとデータ名と列名を示して失敗する。**上位値**（名前の列）は、上位 10 件。`distinctCount` は NULL を除いた異なる値の数で、一覧が完全かどうかは、一覧の長さが `distinctCount` に等しいかで分かる（地図のカテゴリ別の色分けは `dataConfig.classification.maxCategories` 個までの値で行う） |

全値の列: `land_use`、`operator_type`、`railway_type`、`school_type`、`admin_type`。上位値の列: `municipalities.pref_name`、`stations.operator`、`railways.operator`。ほかの `pref_name`、`line_name` は一覧を付けず、説明に例を書く（一覧が情報を足さないため）。自由な文字列（`address`、`station_name`、`school_name`、`city_name`、`muni_name`）と `muni_code` には付けない。

文章は日本語で、`scripts/data/catalog.config.ts` に置く。データごとに、題名、1 行が何か、出典、注意（クエリやスタイルの書き方を変えるものだけ）、列ごとの意味（単位、クエリで合わせる値の形）。出典の名前、URL、年、条件は 1 と 2、注意は 2、5、6.7 の記述による。実測して足した文は 7.6。ファイルに文章のない列がある場合も、文章にあってファイルにない列がある場合も、名前を示して失敗する。
