## リスクと対策

- スパイク A が不合格になる（往復が遅い、並列の呼び出しで破綻する）: 「一方通行のコマンド + SQL エラーを次の発話に添える」方式に切り替える。Phase 4 のタスクを組み直し、ユーザーに確認する。
- S12 などの利用条件に制限がある: Task 0.2 で判明した時点で差し替え案を示し、判断を仰ぐ。デモの用途（社内検証か、外部公開か）で可否が変わるため、勝手に決めない。
- S3 の Range 読み取りができない: 発生した（Task 0.6）。全体取得に統一した（Task 0.7）。ファイルが数十 MB に育ったら読み取り方式を見直す。
- 行政区域の簡素化で境界に隙間が出る: mapshaper に切り替える（Task 1.3）。
- 学校の全国表示（数万点）が GeoJSON では重い: 上限値を下げ、LLM に絞り込みか集計を促す。受け入れテストの 1 件目は成否の基準を見直す。
- LLM の SQL が DuckDB spatial の方言とずれる: エラーとヒントを返して修正させる。頻出の誤りはプロンプトに書く（Task 5.2）。
- 15 秒以内の目標に届かない: 仮の目標なので、計測値を記録したうえで見直す。原因が往復の回数であれば、プロンプトで下調べを減らす。
- `AppSetting` がローカルや E2E で扱いにくい: Task 1.2 で判明した時点で、代替（`KVStore` など）を示して判断を仰ぐ。
- Bedrock の課金: 呼び出し上限と利用許可ユーザーで抑える。検証シナリオの実施回数を記録する。
- デプロイ先のユーザー作成（ブロックのテーブルへの直接書き込み）が動かない（Phase 1 開始前に追加。ユーザーの指示: サインアップ不可）: 未確認で、Task 5.3 で確かめる。動かなければ止めて再検討する。代替は `AuthCognito` の自己サインアップ無効だが、ローカルの mock が手作りのサインアップを通すので、要件をローカルで試験できない。判断はユーザーに仰ぐ。
- Haiku の SQL・スタイルの生成やツール呼び出しの精度が足りない（Task 0.7 で追加）: モデルは Haiku で固定（ユーザーの決定）。プロンプトとスキーマを小さなモデル向けに絞り、Task 4.5 と Task 5.1 で評価する。足りない場合はユーザーに報告して判断を仰ぐ。
- DuckDB-WASM（約 34 MB）をアプリのオリジンから配信できない（Task 0.7 で追加）: ホスト型プレビューの前面は返せなかった。バケットから署名付き URL で読み込む。CloudFront 前面からの配信は、本番のホスティングを最初に行うときに測る。
- 推定時間の超過: Phase 6（フェーズ 2）は Phase 5 の完了後に着手を確認するので、そこで範囲を調整できる。
